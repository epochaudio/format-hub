# 主题收敛与表达能力增强计划

## 背景

Format Hub 当前的主题系统按“系列 × 颜色”组织，形成 5 大系列、35+ 个排版主题。这个设计在早期能快速扩展视觉风格，但继续增长会带来三个问题：

- 用户选择成本变高：用户真正关心的是文章场景，而不是某个系列下的某个颜色。
- 维护成本变高：颜色变体会复制大量相似 CSS，后续修复排版问题需要跨主题同步。
- 产品重心偏移：排版工具的核心价值应该是让内容更清楚、更可交付，而不是积累皮肤数量。

新的方向是：砍掉颜色矩阵，保留场景主题；把复杂度从“皮肤数量”转移到“表达能力”。

## 目标

1. 将主题系统从 35+ 个颜色变体收敛到 8 个高质量场景主题。
2. 让每个主题都有明确的写作场景、排版目标和默认取舍。
3. 引入结构化内容组件，让用户用 Markdown 写出更清楚的摘要、提示、对比、步骤、FAQ、风险、时间线等表达结构。
4. 强化导出 HTML 的“作品属性”，让它不仅能粘贴到公众号，也能作为可归档、可预览、可交付的独立文档。
5. 保持当前 Markdown、富文本复制、PDF 导出能力稳定，不为了重构而扩大风险。

## 非目标

- 不重写为纯静态 HTML 应用。
- 不在第一阶段引入复杂主题编辑器。
- 不把所有历史主题继续以隐藏方式保留在 UI 中。
- 不引入新的 Markdown 解析框架，除非现有 `marked` + 预处理模式无法支撑结构化组件。

## 设计原则

- 简单胜于复杂：用少量高质量主题覆盖主流场景。
- 显式胜于隐式：主题命名、组件语法和导出模式都应该直接表达用途。
- 结构胜于补丁：主题 CSS 应从“复制变体”转向“语义 token + 场景规则”。
- 第一性原理：先问文章为什么需要这个样式，再决定是否添加视觉元素。

## 主题迁移策略

第一阶段不删除渲染能力，只收敛 UI 可选项：

1. 新增 8 个场景主题键。
2. 将默认主题改为 `default-reading` 或 `longform-research`，具体由实际视觉效果决定。
3. 在代码内保留旧主题到新主题的迁移表，用于读取本地存储中的历史主题键。
4. 用户历史主题如果不在新集合中，自动映射到最接近的场景主题。
5. README 和界面文案不再宣传“35+ 种主题”，改为“8 个场景主题”。

后续确认稳定后，再删除旧主题 CSS 或将其拆解为 token 来源。

## 表达组件

结构化表达组件是这次调整的核心。主题减少后，用户仍然应该获得更强的内容表达能力。

### 第一批组件

| 组件 | 用途 | 建议语法 | 渲染目标 |
| --- | --- | --- | --- |
| 摘要 | 文章开头提炼核心观点 | `:::summary` | 稳定醒目的摘要块 |
| 提示 | 补充说明、经验提醒 | `:::note 标题` | 轻量提示框 |
| 洞察 | 强调判断、观点、结论 | `:::insight 标题` | 高权重观点块 |
| 风险 | 风险、限制、注意事项 | `:::risk 标题` | 清楚但不过度警告 |
| 步骤 | 操作流程、方法论 | `:::steps` | 编号步骤块 |
| 对比 | 方案比较、优劣分析 | `:::compare` | 对比卡片或表格 |
| FAQ | 问答整理 | `:::faq` | 问题和答案分组 |
| 术语 | 概念解释 | `:::term 名称` | 术语卡片 |
| 时间线 | 阶段路径、项目节奏 | 继续增强 `{{时间标记}}` | 阶段标签和路径感 |

### 语法示例

```markdown
:::summary
这篇文章的核心结论是：主题数量应该减少，表达结构应该增强。
:::

:::insight 为什么不是继续加主题？
用户选择主题时，本质上是在选择文章场景。颜色变体无法替代场景判断。
:::

:::risk 迁移风险
历史本地存储中的主题键需要映射到新主题，否则用户打开应用时可能丢失偏好。
:::
```

### 实现建议

1. 在 Markdown 渲染前增加显式容器语法预处理。
2. 将组件转换为语义 HTML，例如 `<section class="content-block content-block-insight">`。
3. DOMPurify 白名单补齐必要标签和属性，避免结构被清理掉。
4. 所有主题统一支持这些组件，但视觉权重按场景主题调整。
5. 富文本复制继续以内联计算样式为准，确保粘贴到公众号编辑器后结构不丢失。

## 借鉴 html-effectiveness 的产品洞察

`html-effectiveness` 的关键价值不是“单个 HTML 文件”，而是把内容变成可打开、可交互、可复制、可交付的工作产物。Format Hub 可以吸收三点：

1. 样张化：提供主题样张库，同一篇 Markdown 同时展示 8 个主题的缩略预览。
2. 交付化：导出 HTML 区分公众号粘贴版、独立阅读版、PDF 版。
3. 可验证：用固定样例覆盖代码、公式、图表、脚注、表格、表达组件，作为视觉回归样张。

## 实施计划

### 阶段 1：文档与决策固化

- 新增本计划文档。
- 更新 README 的主题系统说明。
- 明确“8 个场景主题 + 表达组件”的产品方向。

验收标准：

- README 不再描述 35+ 颜色矩阵为未来方向。
- 详细计划可独立解释为什么收敛、收敛到什么、如何迁移。

### 阶段 2：主题收敛

- 新增 8 个场景主题配置。
- 保留代码主题独立选择。
- 新增旧主题到新主题的映射。
- UI 下拉框改为场景主题列表。
- 默认示例内容覆盖新场景主题的关键样式。

验收标准：

- 用户只能从 8 个场景主题中选择。
- 旧本地存储主题键可以自动迁移。
- 富文本复制、HTML 导出、PDF 导出仍可用。

### 阶段 3：表达组件

- 实现 `:::` 容器语法预处理。
- 新增摘要、提示、洞察、风险、步骤、FAQ、术语等组件样式。
- 更新默认 Markdown 示例。
- 更新 README 的扩展语法说明。

验收标准：

- 每个组件都能在预览、复制、HTML 导出、PDF 导出中保持结构。
- 未闭合或未知组件有稳定降级行为。
- 组件不会破坏代码块、Mermaid、KaTeX、脚注。

### 阶段 4：主题样张库

- 新增样张视图或主题选择弹层。
- 同一份 Markdown 批量渲染 8 个主题缩略预览。
- 支持一键切换主题。

验收标准：

- 用户无需逐个切换下拉框即可比较主题。
- 样张视图不明显拖慢编辑体验。

### 阶段 5：导出模式增强

- 保留公众号富文本复制。
- HTML 导出区分“公众号 HTML”和“独立阅读 HTML”。
- 独立阅读 HTML 可包含更完整的页面外壳、标题和基础元信息。

验收标准：

- 公众号版保持粘贴兼容。
- 独立阅读版打开后是一份完整可读文档。

## 风险与缓解

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 旧主题用户偏好丢失 | 用户打开后主题变化突兀 | 增加迁移表和合理默认值 |
| 表达组件语法误伤代码块 | 代码示例被错误解析 | 预处理跳过 fenced code block |
| 公众号编辑器丢样式 | 粘贴结果不稳定 | 继续使用计算样式内联 |
| 主题减少导致用户觉得选择变少 | 感知价值下降 | 用样张库和表达组件提升真实能力 |
| CSS 继续膨胀 | 维护成本没有下降 | 后续拆成 token 和场景规则 |

## 推荐执行顺序

1. 完成文档更新。
2. 做主题收敛，不碰表达组件。
3. 构建验证和手动试用复制 / 导出。
4. 再做表达组件。
5. 最后做样张库和导出模式增强。

这个顺序的好处是每一步都有清楚收益，也能在出现问题时快速定位是哪一层引入的变化。
